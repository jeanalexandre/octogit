# octogit

Octogit est un client Git de bureau pour macOS : il explore l'historique d'un dépôt et protège l'identité de commit selon le profil choisi.
Application Tauri 2 (cœur Rust) avec une interface Svelte 5.

## Prérequis

- macOS 13 ou plus récent, puce Apple
- Rust, version fixée par `rust-toolchain.toml` (installée par `rustup`)
- Node 26.13.0 (fixé par `.nvmrc` : `nvm install`) et pnpm 12.18.0 (`npm i -g pnpm@12` ; corepack ne lance pas pnpm 12)
- le binaire `git` (Command Line Tools de Xcode, Xcode ou Homebrew)
- `cargo-audit` pour `pnpm audit:deps` (`cargo install cargo-audit`)

## Installation

```sh
pnpm install
```

## Lancement

- `pnpm tauri dev` : l'application dans sa fenêtre ; régénère `src/lib/bindings.ts`.
- `pnpm dev:web` : l'interface seule sur `http://localhost:1420` (ou `OCTOGIT_PORT` de `.env.local`) dans le navigateur, avec un pont local qui exécute les vraies commandes Rust (utilisé par Playwright et les captures de revue).

## Ouvrir un dépôt

- Depuis `Welcome` : **Open folder…** (Cmd+O) ouvre le sélecteur de dossier ; la liste **Recent** (nom, chemin, date relative de dernière ouverture, et `ProfileBadge` du profil rattaché ou « No profile »), du plus récent au plus ancien, ouvre un dépôt d'un clic. L'état du badge de chaque récent est lu sans ouvrir le dépôt et sans rien écrire (profil manuel mémorisé, sinon règles ; lecture du `.git/config` local).
- Un dossier qui n'est pas un dépôt Git est refusé par un message qui le nomme ; rien n'est écrit dans ce dossier.
- Dans `History`, le sélecteur de dépôt (`RepoPicker`, le nom du dépôt en haut à gauche) liste les récents et propose aussi **Open folder…** et **Clone…** pour changer de dépôt dans la même fenêtre.
- **Clone…** (Cmd+Maj+C, depuis `Welcome` ou `RepoPicker`) ouvre `CloneDialog` : le profil d'abord (liste dans l'ordre de `ProfileSettings`, aucun sélectionné), l'URL SSH, puis le dossier. Une fois le profil choisi, le dialogue dit « .git/config will get the Pro identity, SSH key and signing. ». Le dossier est pré-rempli par le dernier dossier parent d'un clone réussi (quel que soit son profil, y compris après relance) plus le nom déduit de l'URL (`git@github.com:pro-company/client-git.git` donne `<parent>/client-git`) ; il est vide au tout premier clone ; **Choose…** ouvre le sélecteur de dossier et change le dossier parent. Clone reste désactivé tant qu'un profil, une URL ou un dossier manque. Échap ou Cancel ferment le dialogue sans rien écrire. Le clone (crate `git`, fonction `clone`, binaire `git` en sous-processus, jamais de saisie demandée) reçoit la clé du profil par la variable d'environnement `GIT_SSH_COMMAND`, jamais par `core.sshCommand` : le `.git/config` du clone ne garde que ce qu'écrit ensuite le rattachement. Le profil est mémorisé comme rattachement manuel (prioritaire sur les règles), puis le dépôt est ouvert : identité, `core.sshCommand` et signature du profil sont écrits dans le `.git/config` local avant l'affichage de `History`, et le dépôt passe en tête de Recent (réouvert au lancement suivant). Si l'écriture du profil échoue (clé `.pub` absente pour une signature cochée), le dossier cloné est gardé, rien n'est supprimé, et `History` s'ouvre avec un badge non conforme ; Commit et Push restent bloqués. Sans profil, le dialogue affiche « No profile yet » et **Create profile…** (Clone reste désactivé : aucun clone sans profil) ; ce bouton ouvre `ProfileSettings` sur son formulaire de création, et après Save `CloneDialog` revient avec le nouveau profil sélectionné et l'URL et le dossier déjà saisis (l'état vit dans `App.svelte`). `Welcome` sans profil propose aussi **Create a first profile**, qui ouvre ce même formulaire. Une URL `https://github.com/org/app.git` (ou `http://`, avec ou sans `.git`) affiche « Use git@github.com:org/app.git? », case cochée par défaut : cochée, le clone utilise l'URL SSH (`git remote get-url origin` rend `git@github.com:org/app.git`) avec la seule clé du profil (`ssh -F none -i <clé> -o IdentitiesOnly=yes -o IdentityAgent=none` : l'agent SSH est ignoré) ; décochée, le clic sur Clone est refusé avec un message, rien n'est cloné ni écrit. L'URL saisie reste affichée telle quelle. Une URL `https://` d'un autre hôte est refusée (« Only github.com URLs can be cloned over HTTPS (converted to SSH). ») ; la conversion est `github_ssh_url` du crate `git` (reprise en TypeScript, `githubSshUrl`, pour l'affichage de la case). Pendant le clone, le dialogue dit « Cloning client-git with profile Pro… » avec une barre de progression et « 9 / 20 objects » (événement `clone-progress`, lu dans la sortie de `git clone --progress` ; `git` est lancé avec `LC_ALL=C` pour que cette sortie soit en anglais ; sous 100 objets, `git` affiche « Unpacking objects » au lieu de « Receiving objects », les deux sont lus). **Cancel** (commande `cancel_clone`) arrête `git clone` (SIGTERM, puis SIGKILL après 2 s) : le dossier de destination revient à son état d'avant (absent s'il n'existait pas, avec les dossiers parents que `git` a créés ; vide s'il existait vide), aucun Recent, dernier dossier parent ni rattachement n'est écrit, et la saisie revient sans message d'erreur. Un seul clone à la fois. Tout autre échec affiche « Clone failed: » et la sortie brute de `git`, le dialogue reste ouvert avec ses champs, et rien ne reste sur le disque.
- Le dépôt ouvert passe en tête de Recent ; au lancement, Octogit rouvre le dernier dépôt ouvert (`repositories.json`, version 6 ; les versions 1 à 5 sont migrées à la lecture). Le champ `last_clone_parent` (version 6) mémorise le dossier parent du dernier clone réussi ; absent avant, il laisse le dossier vide.
- En test (`pnpm dev:web`, Playwright), le sélecteur natif est remplacé par le dossier posé dans `window.__octogitChosenFolder`.

## Graphe de `History`

- Le graphe est une liste virtualisée (seules les lignes visibles, plus quelques-unes de marge, existent dans le DOM) : lanes colorées tracées en SVG par ligne, nœuds en cercle aux initiales de l'auteur (un stash : carré à icône d'archive, sans initiales), dates relatives (heure absolue au survol), barre d'aide en pied. Jusqu'à 10 000 commits sont lus.
- Un clic droit sur l'en-tête (au clavier : touche menu ou Maj+F10 depuis l'en-tête qui a le focus) masque ou réaffiche les colonnes auteur, date et SHA ; le choix est gardé dans `preferences.json` (champ `hidden_columns`) sous `OCTOGIT_DATA_DIR`.
- Le graphe part de HEAD et de toutes les refs (branches locales, `origin/…`, tags, stashes) ; chaque ref est une étiquette (`RefLabel`) dans la colonne de gauche, reliée par un fil au nœud de son commit, et une entrée de `BranchSidebar`. Le stash est un nœud dont seul le premier parent est gardé. L'avance et le retard de la branche courante sur sa branche distante suivie (`branch.<nom>.remote` et `.merge`) s'affichent en en-tête ; sans suivi, « Not published » à la place du compteur.
- La colonne des refs garde 180 px. Chaque commit n'y montre qu'une `RefLabel`, la prioritaire (courante, sinon locale, sinon distante seule, sinon tag), tronquée en fin par « … », suivie de « +n » pour les n autres refs ; une locale et son `origin/…` sur le même commit restent une seule étiquette à deux icônes. Au survol ou au focus clavier de l'étiquette, toutes les étiquettes de la ligne s'affichent entières, empilées par-dessus le graphe, dans leur variante. Le nom d'auteur est focalisable et son infobulle affiche « Nom <adresse> » (au survol et au focus), ouverte au-dessus du nom, bord gauche sur la colonne Auteur, sans recouvrir le message de la ligne.
- Un clic sur un commit ouvre `CommitDetail` à droite : message, auteur, date, SHA, « Signed » (en-tête `gpgsig` présent, validité non vérifiée) ou « Not signed », fichiers modifiés en M / A / D (merge : par rapport au premier parent ; renommages non détectés).
- La ligne WIP ouvre le graphe, au-dessus du premier commit (nœud en pointillés, lié à la lane du commit que HEAD désigne) ; elle n'existe que s'il y a des changements, est alors sélectionnée à l'ouverture de dépôt et porte « n changed files » (« 1 changed file » ; un fichier à la fois indexé et modifié compte une fois). Sur un arbre propre, il n'y a pas de ligne WIP : le dernier commit de la branche courante est sélectionné, avec son `CommitDetail` (« No changes » n'existe plus). La ligne revient en moins de 1 s quand un changement apparaît, y compris hors d'Octogit, sans changer la sélection ni le panneau ; elle disparaît quand l'arbre redevient propre (le dernier commit, ou le commit qui vient d'être créé, est alors sélectionné). Échap ne quitte pas la ligne WIP. Un dépôt sans commit n'affiche que cette ligne (plus de « No commits yet. »). Sélectionnée, elle montre `WorkingChanges` à droite à la place de `CommitDetail` : « Unstaged · n » (modifiés, supprimés, non suivis comptés comme ajoutés) avec **Stage all**, « Staged · n » avec **Unstage all**, chaque fichier avec sa lettre M / A / D et son chemin ; dépôt sans commit et arbre propre : « Working tree clean. », Commit désactivé (Stash vient avec S-32). Stage all lance `git add --all` (fichiers non suivis compris), Unstage all `git reset --quiet` ; l'état se lit avec `gix` (sans renommage, l'index n'est pas réécrit).
- Sous les listes, `WorkingChanges` a les champs **Summary** et **Description**, la case **Amend last commit** et le bouton **Commit to \<branche\>** (Cmd+Entrée depuis un des deux champs fait de même). Le commit part par le binaire `git` (`git commit -F -`, message = résumé, ligne vide, description) : auteur, committer et signature viennent du `.git/config` local, rien n'est écrit dans `~/.gitconfig`, et rien n'est indexé automatiquement. Commit est désactivé avec « Summary required » (résumé vide) ou « No staged changes » (rien d'indexé). Après le commit, Staged se vide, les fichiers non indexés restent, les champs se vident et le nouveau commit est en tête du graphe. Quand le dépôt est rattaché à un profil conforme, « ✓ Identity matches profile Work · <user.email> » s'affiche sous le bouton. **Identité non conforme** (une des quatre valeurs du `.git/config` local diffère du profil, y compris changée au terminal après l'ouverture) : `WorkingChanges` affiche « Identity does not match profile Work. », puis, pour chaque valeur en écart, « Expected: <valeur du profil> » et « Found in .git/config: <valeur locale> » (« (not set) » si absente), et **Fix repository identity** ; Commit est désactivé, Cmd+Entrée et Amend ne créent rien, et le badge passe en « ⚠ … identity mismatch ». Le cœur refuse aussi le commit au moment où il est lancé (`Identity does not match profile Work.`), sans se fier à l'affichage : `git log` reste inchangé. **Fix repository identity** écrit les valeurs du profil comme Overwrite (clés ciblées, reste du `.git/config` intact) ; Commit redevient disponible et « Identity matches profile Work » s'affiche. Le blocage d'un dépôt sans profil, de Push et des autres opérations vient avec S-21 et suivantes. Cocher **Amend last commit** remplit les champs avec le message du dernier commit (modifiables) ; décocher rend le brouillon saisi avant, à l'identique ; Commit remplace alors le dernier commit (`git commit --amend`, nouveau SHA, même parent, fichiers indexés et message saisi). Un refus de Git (hook, signature) affiche la première ligne de sa sortie.
- **Corriger le message du dernier commit depuis `CommitDetail`** : sur arbre propre, le `CommitDetail` du dernier commit de la branche courante a les champs **Summary** et **Description** pré-remplis de son message (modifiables) et le bouton **Amend \<sha\>** (sha abrégé à 7 caractères, Cmd+Entrée depuis un des deux champs fait de même) ; pas de bouton Commit. Amend est désactivé tant que le message est identique à l'origine, et si Summary est vide (« Summary required »). Sous le bouton : « ✓ Identity matches profile Work · <user.email> », ou, dépôt non conforme, « Identity does not match profile Work. » avec **Fix repository identity** (sans lignes Expected / Found), ou « No profile » (sans lien) : Amend reste désactivé et le cœur refuse aussi l'action (`git log` inchangé). Seul le message change : `git commit --amend --only --reset-author -F -` sans chemin (commande `amend_message`, `amend_message` de la crate `git`), le commit garde son parent et les fichiers de `HEAD`, l'index et l'arbre de travail sont intacts, l'auteur d'origine est remplacé par l'identité du profil (auteur, committer et signature viennent du `.git/config` local). Le commit réécrit est ensuite sélectionné, formulaire pré-rempli de son nouveau message. Le formulaire est décidé à la sélection : une ligne WIP qui apparaît pendant la saisie ne le retire pas, une autre sélection le fait disparaître ; le dernier commit sélectionné avec des changements est en lecture seule (l'Amend passe par **Amend last commit** de `WorkingChanges`). Un autre commit n'a jamais ces champs. Tests : `crates/git/tests/commit.rs`, `src-tauri/tests/commit_guard.rs`, `src/lib/components/CommitDetail.test.ts`, `src/lib/screens/History.test.ts`, `e2e/amend-detail.spec.ts` (fixtures existantes).
- L'arbre de travail est surveillé par la crate `notify` (FSEvents) sur le dépôt et son `.git/` : une rafale d'écritures (100 ms de calme, 400 ms au plus) donne une seule relecture, et l'interface reçoit l'événement `working-tree-changed` (charge `WorkingTreeChanged`) si la liste des fichiers a changé, en moins de 1 s, sans geste. Les écritures d'Octogit (Stage all, Unstage all) ne sont pas signalées : leur résultat est déjà affiché. La même surveillance compare le contenu de `.git/config` après chaque rafale et envoie l'événement `repo-config-changed` (charge `RepoConfigChanged`, le chemin du dépôt) quand il a changé ; l'interface relit alors l'écart d'identité (`get_identity_mismatch`), de même qu'au retour dans la fenêtre. En `pnpm dev:web`, le pont lance un processus `octogit-bridge watch_working_tree <dépôt>` par page (flux `/__bridge-events/working-tree-changed`) qui joue le rôle des événements Tauri : une charge sans `tree` est `repo-config-changed`.
- `BranchSidebar` montre ses sections dans l'ordre fixe Local, `origin`, les autres remotes par ordre alphabétique, Tags, Stashes. Les noms sont groupés par chemin en dossiers dépliables (`feat/ui/x` : dossier « feat · 3 » contenant le dossier « ui · 1 »), avec le compte de toutes les refs dessous ; à chaque niveau, les dossiers viennent avant les noms. Seuls les dossiers sont triés par ordre alphanumérique sans tenir compte de la casse ; tous les autres éléments (branches locales et distantes, tags, stashes) vont du plus récent au plus ancien (date du commit désigné, à date égale par nom), la branche courante à sa place dans cet ordre ; un dossier ne prend pas la date de son élément le plus récent. Les stashes ne sont pas groupés. Les dossiers sont dépliés par défaut ; un clic les replie ou les déplie.
- L'état des dossiers est mémorisé par dépôt dans `repositories.json` (champ `collapsed_folders` : chemin du dépôt, puis clés `section:chemin` des dossiers repliés), écrit à chaque clic ; un échec d'écriture est ignoré. Le fichier est en `version` 4 (voir la largeur du graphe plus bas) ; les versions 1 à 3 sont migrées à la lecture (exemples versionnés dans `crates/store/tests-data/`).
- Largeur du graphe : la colonne des lanes affiche par défaut toutes les lanes du dépôt, dans la limite de 40 % de la zone du graphe (la liste des commits : colonne des refs, lanes, message, sans `BranchSidebar` ni panneau de droite). Quand des lanes dépassent, elles sont coupées et un fondu (dégradé vers la surface, sans couleur propre) au bord droit les signale. Cette largeur par défaut est calculée à l'ouverture du dépôt puis figée : un fetch qui ajoute des lanes ne la change pas (les nouvelles sont coupées, avec le fondu) ; rouvrir le dépôt la recalcule.
- La colonne du graphe mesure au moins 64 px, au défaut comme au glisser (un dépôt à une seule lane : 64 px, l'en-tête « Graph » entier) ; une largeur mémorisée plus petite est affichée à 64 px, sans réécrire `repositories.json`.
- Le séparateur entre le graphe et le message (rôle `separator`, `aria-label` « Resize graph ») se glisse à la souris (la largeur suit le pointeur, écrite à la fin du glisser) ou se règle au clavier (focus, flèches gauche et droite : une lane par appui). Un double-clic dessus revient au défaut, recalculé sur les lanes présentes. La largeur réglée est mémorisée par dépôt dans `repositories.json` (champ `graph_widths` : chemin du dépôt, puis largeur en pixels ; absent : défaut), un échec d'écriture est ignoré.
- Chaque section de `BranchSidebar` prend la hauteur de ses lignes (une ligne de dossier compte comme une ligne), 8 lignes au plus : au-delà, elle défile seule. Cette hauteur par défaut est calculée à l'ouverture du dépôt puis figée (un fetch qui ajoute une branche ne la change pas ; rouvrir le dépôt la recalcule). La branche courante est amenée en vue à l'ouverture. Une section vide n'affiche que son en-tête.
- Le bord bas d'une section se glisse à la souris (la hauteur suit le pointeur, écrite à la fin du glisser) ou se règle au clavier (rôle `separator`, focusable, flèches haut et bas : une ligne par appui). Un double-clic sur ce bord revient à la hauteur par défaut, recalculée sur les lignes présentes. Un clic sur l'en-tête d'une section la replie (en-tête seul) ou la déplie, écrit tout de suite. Replier une section ou un dossier ne retire aucune ref du graphe.
- Hauteurs et repli des sections sont globaux (communs à tous les dépôts), dans `preferences.json` : `section_heights` (hauteur en pixels par identifiant de section : `local`, `remote:<nom>`, `tags`, `stashes` ; absent : hauteur par défaut) et `collapsed_sections` (identifiants des sections repliées), avec `hidden_columns`. Le fichier passe en `version` 4 (`sync_action` : voir « Fetch automatique ») ; les versions 1 (colonnes seules) à 3 sont migrées à la lecture (exemples versionnés dans `crates/store/tests-data/`). Un échec d'écriture est ignoré.
- Le bouton en tête de `BranchSidebar` replie le panneau en une bande d'une icône par section (Local, chaque remote, Tags, Stashes ; le nom de la section est l'infobulle et l'étiquette accessible) ; le bouton de la bande le rétablit. Aucun raccourci clavier ne le replie. L'état est global (tous les dépôts), écrit au clic dans `preferences.json` (`panel_collapsed`).
- Panneau replié, un clic sur une icône ouvre la section dans un volet flottant posé par-dessus le graphe (le graphe ne bouge ni ne change de taille), avec les mêmes gestes que le panneau. Échap (le focus revient à l'icône) ou un clic hors du volet le ferme, ainsi qu'un checkout lancé depuis le volet (le focus revient aussi à l'icône) ; un checkout lancé depuis le panneau déplié ne ferme ni ne replie rien.
- Checkout d'une branche (jamais de HEAD détachée : `git switch`, qui refuse de détacher). Quatre gestes, tous au clavier aussi : double-clic (ou Entrée) sur une branche locale ou une `origin/…` de `BranchSidebar`, double-clic sur la `RefLabel` d'une branche du graphe, choix dans le sélecteur de branche de l'en-tête de `History` (bouton « Switch branch : <courante> », liste filtrable par ce qu'on tape, flèches et Entrée), et clic droit (touche menu ou Maj+F10) › Checkout du `RefContextMenu`. Les modifications compatibles gardent leur état d'indexation ; si Git refuse (modifications qui seraient écrasées), rien ne change et un message d'une ligne s'affiche sous l'en-tête (« Checkout failed. », textes définitifs : S-51 et S-53). Tags et stashes n'ont aucun geste de checkout.
- Checkout d'une `origin/<b>` : sans locale `<b>`, elle est créée sur le même commit et suit `origin/<b>` (0 / 0) ; avec une locale `<b>` sur le même commit, c'est son checkout, sans rien créer ni déplacer ; avec une locale sur un autre commit (qu'elle suive ou non), une confirmation « <b> already exists locally. Reset it to origin/<b>? » liste les commits de `<b>` absents de la distante (SHA abrégé, résumé) sans rien modifier : « Reset and checkout » remet `<b>` sur `origin/<b>` (avec suivi) puis la checkoute, « Checkout local as is » checkoute `<b>` sans la déplacer, Cancel ou Échap ne change rien. Aucun checkout ne crée de commit ni ne pousse. Côté Rust : `crates/git/src/checkout.rs` (`plan_checkout`, `checkout`), commande `checkout_repository` (rend le dépôt relu ou la confirmation à trancher), tests dans `crates/git/tests/checkout.rs` sur `fixtures/refs.sh` (les cas qu'elle ne couvre pas sont fabriqués dans les tests, aucun script ajouté).
- Créer une branche (jamais de HEAD détachée, aucun suivi de branche distante, aucun commit, rien de poussé). Deux gestes, tous au clavier aussi : le bouton Branch de `Toolbar` (à côté du sélecteur ; désactivé sans branche courante) crée sur le sommet de la courante, et « Create branch here » (clic droit, touche menu ou Maj+F10 sur une ligne de commit du graphe : `RefContextMenu` du commit ; bouton de `CommitDetail`) crée sur ce commit. Un champ de saisie en ligne prend la place des étiquettes de la ligne du commit : Entrée crée la branche et la rend courante (en « Not published »), Échap le ferme sans rien créer (le focus revient au geste d'origine). Le nom est vérifié pendant la saisie : « Branch develop already exists. » (nom d'une branche locale) ou « Invalid branch name. » (refusé par Git : `feature graph`, `feature..x`…) s'affiche sous le champ et Entrée est sans effet tant qu'un message est affiché ; Entrée revérifie le nom avant de créer. Un nom égal à celui d'une `origin/…` sans locale est accepté : la locale créée ne la suit pas. Un nom plus long que la colonne des refs élargit le champ par-dessus le graphe, la colonne garde 180 px. Si Git refuse (modifications qui seraient écrasées en créant sur un autre commit), rien ne change et un message d'une ligne s'affiche sous l'en-tête (textes définitifs : S-51 et S-53). Blocage par l'identité : jamais (aucun commit n'est créé). Le champ est l'état « saisie en ligne » de `RefLabel` (Rename et Create tag le reprendront). Côté Rust : `crates/git/src/branch.rs` (`check_branch_name`, `create_branch` : `git check-ref-format` puis `git switch --no-track -c`), commandes `check_branch_name` et `create_branch_repository`, tests dans `crates/git/tests/branch.rs` sur `fixtures/refs.sh`, e2e dans `e2e/branch.spec.ts` (aucune fixture ajoutée).
- Un clic sur un fichier de `CommitDetail` ouvre `DiffView` (mode commit, lecture seule, par-dessus `History` qui reste monté dessous) : diff du fichier dans ce commit, par rapport au premier parent (arbre vide pour un commit racine, renommages non détectés), côte à côte par défaut (non mémorisé) ou unifié par la commande segmentée ; lignes ajoutées et supprimées marquées « + » et « − » (pas par la couleur seule) ; « File i / n » encadré de Previous file / Next file (désactivés au premier et au dernier fichier de la liste du commit) ; fichier ajouté ou supprimé : un seul côté ; fichier binaire (octet nul, comme Git) : « Binary file · 7 B → 11 B. No text diff. », sans contenu. Échap (ou « Back to graph ») ramène à `History` avec le même commit sélectionné et la même position de défilement du graphe. Le diff se lit avec `gix` (fonctionnalité `blob-diff`, algorithme de Myers) dans `crates/git/src/diff.rs` (`read_file_diff`), commande `commit_file_diff` ; pas d'indexation depuis le mode commit (lecture seule), pas de seuil « trop gros » (S-55). Tests : `crates/git/src/lib.rs`, `src/lib/screens/DiffView.test.ts`, `e2e/diff-view.spec.ts`.
- Un clic sur un fichier de `WorkingChanges` ouvre `DiffView` en mode **travail** (fichier non indexé : arbre de travail contre l'index ; un fichier non suivi est un ajout complet) ou **indexé** (index contre `HEAD`), toujours en unifié, par-dessus `History` (la ligne WIP reste sélectionnée dessous). En-tête : **Stage file** / **Unstage file**, **Stage selected lines** / **Unstage selected lines** (désactivé sans ligne choisie) et « File i / n » parmi les fichiers du groupe cliqué (Previous file / Next file) ; chaque bloc (lignes modifiées consécutives) a sa barre « Hunk k / n » avec **Stage hunk** / **Unstage hunk**. Les lignes se choisissent dans la marge (case à gauche des numéros) : clic ou glissé, Maj+clic pour étendre depuis la dernière ligne choisie, et au clavier (Entrée ou Espace bascule la ligne focalisée, Maj+Entrée étend). Un binaire n'a que Stage file / Unstage file. Après chaque geste, le cœur rend l'état relu : `WorkingChanges`, la ligne WIP et le diff se mettent à jour sans attendre la surveillance. Le dernier bloc passé, `DiffView` reste ouvert sur « No more changes in this file » (Previous / Next file et Échap restent disponibles). Entrée (ou ↓) passe au résultat suivant, Maj+Entrée (ou ↑) au précédent (à partir du commit sélectionné s'il est parmi les résultats, sinon de la position de la recherche), avec retour au premier après le dernier et inversement ; le graphe défile jusqu'au résultat choisi, dont `CommitDetail` s'ouvre. Un SHA complet, ou abrégé d'au moins 4 caractères qui n'en désigne qu'un, sélectionne ce commit sans autre geste. « Show matches only » ne laisse dans le graphe que les lignes des résultats (les lanes restent celles de tout l'historique) ; décoché, toutes les lignes reviennent ; sans résultat, il ne retire rien. Ni la saisie ni la case ne sont mémorisées. Le résumé, l'auteur et le SHA sont cherchés dans l'interface (`src/lib/search.ts`) ; la description ne l'est que dans le cœur : commande `search_commit_messages` (`crates/git`, `search_messages`, même plage de 10 000 commits que le graphe) lancée après une pause de 150 ms dans la frappe. Dépôt pour la recherche : `fixtures/search.sh <dossier>` (120 commits linéaires ; « notify » dans trois résumés et, seul, dans le corps du quatrième ; un auteur unique « Zoé Quillet ») ; `fixtures/large.sh` sert au test sur 10 000 commits. Tests : `crates/git/src/lib.rs`, `src/lib/search.test.ts`, `src/lib/components/SearchBox.test.ts`, `src/lib/screens/History.test.ts`, `e2e/search.spec.ts`.
- Checkout depuis `CommitDetail` : le bouton Checkout n'existe que si le commit porte une branche. Une seule branche locale : elle devient courante ; plusieurs : un menu liste les branches (flèches, Entrée, Échap) et le checkout n'a lieu qu'après le choix ; seulement une `origin/…` : même checkout que celui de cette `origin/…` (création de la locale avec suivi, confirmation si une locale diffère) ; aucune branche : pas de Checkout, « Create branch here » reste proposé. Les tags et stashes du commit ne comptent pas.
- Dépôt avec toutes les refs : `fixtures/refs.sh <dossier>` (tags, stash, `develop` en avance de 2 et en retard de 3 sur un `origin` bare, branche seulement distante, merge, commit signé). `fixtures/sidebar.sh <dossier>` y ajoute les remotes `upstream` et `backup`, les branches `feat/api`, `feat/ui/x` (sur `main`), `feat/graph` (sur `develop`, plus récent) et le tag `v0.9.0`, pour `BranchSidebar`. `fixtures/layout.sh <dossier>` fabrique 23 branches locales (la courante en dernier), 3 branches sur `origin` et aucun tag ni stash, pour la hauteur des sections. `fixtures/wide.sh <dossier>` fabrique 40 branches d'un commit chacune qui partent du même commit (plus de 40 lanes), pour la largeur du graphe.
- Dépôt pour l'indexation fine et Discard changes : `fixtures/stage.sh <dossier>` (`lines.txt` de 20 lignes modifié en trois blocs non indexés, `staged.txt` indexé en deux blocs, `both.txt` avec une ligne indexée et une autre non, `logo.bin` binaire modifié, `lib/ProfileBadge.svelte` non suivi).

## Fetch automatique

- À l'ouverture d'un dépôt (au lancement comme par `RepoPicker`), puis chaque minute tant qu'il reste ouvert, Octogit lance `git fetch --prune` en tâche de fond (binaire `git` du poste : `.git/config` est respecté, jamais écrit). Un seul fetch à la fois par dépôt ; changer de dépôt arrête la planification de l'ancien ; un fetch qui dépasse 30 s est tué ; aucune saisie n'est jamais demandée.
- Le fetch ne modifie jamais une branche locale, `HEAD` ni l'arbre de travail (aucun pull implicite) : seules les refs `origin/…` et les tags distants changent. Une `origin/…` supprimée sur `origin` disparaît du graphe (prune) ; la branche locale qui la suivait reste intacte.
- `FetchStatus`, dans l'en-tête de `History`, affiche « fetched n min ago » : l'âge du dernier fetch réussi, mis à jour sans geste. Un échec garde le dernier âge (états hors ligne et erreur : à venir).
- `SyncButton`, dans l'en-tête de `History` à côté de `FetchStatus`, affiche l'action par défaut suivie d'une flèche. Un clic lance Fetch All : `git fetch --all --prune` (tous les remotes, avec prune), sous la même garde que le fetch automatique (un seul fetch à la fois par dépôt) ; le graphe et `FetchStatus` (qui repart de « just now ») se mettent à jour, aucune branche locale, `HEAD` ni l'arbre de travail ne change. Pendant le fetch, le bouton affiche « Fetching… » et ne se relance pas.
- La flèche ouvre un menu à choix unique (Échap ou un clic ailleurs le ferme) : Fetch All, Pull (fast-forward only), Pull (rebase). Cocher une entrée en fait l'action par défaut et change le libellé, sans rien lancer. Le choix vaut pour tous les dépôts et reste après la relance d'Octogit : `preferences.json` (champ `sync_action` : `fetch_all`, `pull_ff_only` ou `pull_rebase` ; absent : Fetch All).
- Pull (fast-forward only) : `git pull --ff-only` aligne la branche courante sur sa branche suivie (l'indicateur passe à 0 / 0 si elle n'avait pas de commit local). Une divergence est refusée sans rien changer, avec « Branch has diverged: 2 local, 3 on origin. » près du bouton (nombres et remote vrais au moment du refus). Pull (rebase) : `git pull --rebase` rejoue les commits locaux au-dessus de la branche suivie (historique linéaire) ; en cas de conflit (S-40), le rebase reste en cours (aucun commit de fusion, `git status` l'indique) et `ConflictResolver` s'ouvre (`pull_repository` rend `conflict` vrai) ; Abort rebase ramène la branche à son commit d'avant le pull. Jamais de commit de fusion, quels que soient `pull.rebase` et `pull.ff` du `.git/config`. Un Pull passe par la même garde que le fetch (un seul échange réseau à la fois par dépôt), met à jour le graphe, l'arbre de travail et `FetchStatus`, et le bouton affiche « Pulling… » pendant ce temps.
- Sur une branche « Not published » (sans branche suivie), les deux Pull sont désactivés avec la raison « Branch not published. » (infobulle et texte accessible) ; leurs entrées du menu restent cochables et Fetch All reste actif.
- Fetch et Fetch All lisent le `core.sshCommand` du `.git/config` local du dépôt (clé SSH du profil) ; `~/.gitconfig` n'est ni lu pour choisir la clé ni écrit.
- En test, l'intervalle de 60 s se règle par `?fetch_interval_ms=<ms>` dans l'adresse de `pnpm dev:web` (lu par `src/web-bridge.ts`, sans effet dans l'application livrée).

## Push

- `PushButton`, dans l'en-tête de `History` à côté de `SyncButton`, affiche « Push n » quand la branche courante est en avance de n commits sur sa branche suivie. Un clic pousse vers cette branche distante (refspec explicite, `push.default` n'intervient pas) : l'indicateur passe à 0 / 0, `HEAD`, les branches locales et l'arbre de travail ne changent pas, aucun tag n'est poussé. Le push passe par le binaire `git` (donc le `core.sshCommand` du `.git/config` local, jamais `~/.gitconfig`), sous la même garde que le fetch (un seul échange réseau à la fois par dépôt) ; pendant ce temps le bouton affiche « Pushing… » et ne se relance pas.
- Sans commit en avance, le bouton est désactivé, sans compteur, avec la raison « Nothing to push. » écrite à côté.
- Une branche courante sans branche suivie affiche « Not published » dans l'en-tête à la place du compteur, et `PushButton` reste actif : un clic la crée sur `origin` sous le même nom et la fait suivre (`git push --set-upstream`, `branch.<nom>.remote` et `.merge` écrits dans le `.git/config` local). Son `RefLabel` passe de l'état en avance (anneau) à l'état synchronisé et « Not published » disparaît. Le bouton reste actif même sans remote `origin` : le cœur décide au clic d'après `git remote get-url origin` (pas d'après les refs `origin/…`, absentes aussi d'un `origin` vide). Sans `origin`, le clic est refusé et « No origin remote. » s'affiche en message d'une ligne (la liste des remotes viendra avec S-55).
- Si la distante a reçu des commits d'un autre clone, le push est refusé, la branche distante ne change pas, et « origin has commits you do not have locally. » s'affiche près du bouton. Octogit ne force jamais ici : « Force push » n'est proposé qu'après une réécriture locale de commits déjà poussés (voir ci-dessous). Push est bloqué quand l'identité du dépôt est non conforme ou « No profile » (voir « Profils » : bloquer Commit et Push). Un autre échec (délai de 30 s dépassé, `git` introuvable) affiche un message d'une ligne et ne change rien.
- Push est aussi bloqué par les **commits à pousser fautifs** : voir « Profils » (« Commits à pousser »). Dans cet état, « Fix commit identity » les corrige en un geste, puis Push redevient un push normal (jamais Force push) : voir « Profils » (« Fix commit identity »).

- **Force push** : quand des commits déjà poussés ont été réécrits en local (Amend, rebase, reset, terminal compris), `PushButton` affiche « Force push » (bordure pointillée de 2 px) au lieu de « Push n ». La réécriture est lue par la commande `get_force_push_check` (crate `git`, `read_rewrite`) : les commits de la branche distante absents de la branche locale qui ont figuré dans son reflog. Aucune réécriture si la branche n'a pas de suivi, si elle n'est pas en retard, ou si un commit distant en trop n'a jamais été local (distant avancé par un autre clone, même combiné à une réécriture) : le push reste alors refusé, jamais de force, jusqu'à ce que ce commit soit intégré par un pull en rebase. Le clic ouvre `ForcePushDialog` : « Force push feature/profiles to origin? », « 2 commits on origin/feature/profiles will be overwritten: », puis chaque commit écrasé (SHA abrégé, résumé). Cancel ou Échap ferment sans rien pousser. Force push lance `git push --force-with-lease=<branche distante>:<SHA de la ref de suivi lu à l'ouverture du dialogue>` (commande `force_push_repository`) : jamais `--force` seul, et un fetch lancé entre-temps n'élargit pas le bail. Si le distant a reçu un commit depuis ce SHA, Git refuse, rien n'est écrasé, et le dialogue dit « Force push refused », « origin/feature/profiles received a commit since the last fetch. Nothing was overwritten. », avec Details (sortie brute de Git) et Close seul. Réussi, l'indicateur passe à 0 / 0 et `PushButton` est désactivé. Même garde que le fetch et le push ; le garde d'identité et celui des commits à pousser (`ensure_pushable`) sont refaits côté Rust en tête de `force_push_repository`, avant tout `git push` : un dépôt non conforme, « No profile » ou un commit fautif refuse le force push (bare inchangé), même si le dialogue est déjà ouvert ; `core.sshCommand` du `.git/config` local. Fixture : `fixtures/force-push.sh <dossier> [scénario]` part de `push.sh ahead`, pousse les 2 commits locaux puis les réécrit : `pushed` (défaut, aucune réécriture), `amend`, `squash`, `rebase` ou `reset` ; `<dossier>-other` peut ensuite pousser un commit sur `origin/develop` sans que le dépôt le sache.

## Profils

- **Cmd+,** ouvre `ProfileSettings` depuis `History` ou `Welcome` ; Échap revient à l'écran d'origine. Depuis `History`, l'écran s'ouvre sur le profil actif du dépôt (le premier de la liste s'il n'en a pas) ; `Welcome` a aussi un bouton **Profiles** (Cmd+,), et le menu du badge a **Edit profiles…**. Sans profil, seul « Create a first profile » s'affiche (Name, `user.name`, `user.email`, SSH key choisie ou générée, voir plus bas ; `user.name` vide par défaut, rien repris de `~/.gitconfig`). Ensuite : liste des profils (pastille de couleur, nom, `user.email`), **New profile**, et pour le profil sélectionné nom, couleur (une des 6 couleurs de lanes), `user.name`, `user.email`, signature des commits et chemin de la clé, enregistrés par **Save** (désactivé si `user.name` ou `user.email` est vide).
- **Clé SSH du profil** : **Choose…** ouvre le sélecteur de fichier dans `~/.ssh` et affiche le chemin et l'empreinte `SHA256:` de la clé (celle de `ssh-keygen -lf`) ; **Generate ed25519…** crée `~/.ssh/id_ed25519_<nom du profil>` (droits 600) et son `.pub`, avec une passphrase facultative, et refuse, en nommant le fichier, d'écraser un fichier existant ; **Copy public key** met la clé publique (une ligne `ssh-ed25519 AAAA…`) dans le presse-papiers, « to paste in GitHub › Settings › SSH keys ». Une clé existante protégée par une passphrase et sans `.pub` demande sa passphrase une fois : le `.pub` est écrit à côté de la clé privée. Le profil enregistre le chemin de la clé, jamais son contenu ; les clés ne sont jamais supprimées par Octogit. Tout passe par `/usr/bin/ssh-keygen`.
- **Passphrases** : gardées dans le trousseau macOS (service « Octogit SSH passphrase », un élément par chemin de clé), jamais dans un fichier JSON, jamais journalisées ni renvoyées à l'interface, et jamais redemandées. Test manuel du vrai trousseau (non couvert par les tests automatiques) : générer une clé avec passphrase dans `pnpm tauri dev`, vérifier l'élément dans Trousseau d'accès, relancer.
- **Test connection** (à côté de Copy public key) lance toujours `/usr/bin/ssh` (jamais cherché dans le `PATH`) : `ssh -T -F none git@github.com -i <clé du profil> -o IdentitiesOnly=yes -o IdentityAgent=none` : seule la clé du profil est présentée, quel que soit le contenu de l'agent SSH et de `~/.ssh/config` (`-F none`). Réponse « Hi <compte>! You've successfully authenticated… » (même si `ssh` sort en code 1) : « ✓ github.com: authenticated as @<compte> ». Refus : « Test failed: » suivi du message brut de SSH (en mono) et de « Public key not added on GitHub yet? », avec Copy public key et **Test again**. Le bouton garde le focus pendant le test (`aria-disabled`). Aucune réponse : interrompu 10 s après le clic, « No response from github.com after 10 s. », mêmes boutons. Rien n'est jamais demandé en fond : entrée fermée, `BatchMode` sans passphrase ; la passphrase du trousseau passe par `SSH_ASKPASS` qui lit un tube nommé (droits 600), jamais l'environnement ni la ligne de commande ; une clé d'hôte inconnue est acceptée au premier contact (`StrictHostKeyChecking=accept-new`).
- Test de connexion en test : le pont de test lance `fixtures/fake-ssh/ssh` par son chemin (jamais d'appel réel à GitHub ; l'application livrée ne lit aucun chemin dans l'environnement) ; il journalise les options reçues dans `<dossier SSH>/fake-ssh.log` (`FAKE_SSH_LOG`) et répond selon `FAKE_SSH_MODE` : `ok` (« Hi $FAKE_SSH_ACCOUNT! », défaut `octogit`), `denied` (refus), `silent` (silence au-delà de 10 s), `serve` (clone : sert `git upload-pack` sur le dépôt `--bare` `$FAKE_SSH_SERVE_ROOT/<chemin demandé>`, donc `git@github.com:org/app.git` sur `<racine>/org/app.git` ; `FAKE_SSH_ALLOWED_KEY` n'accepte que cette clé, présentée avec `-o IdentitiesOnly=yes -o IdentityAgent=none`, sinon « Permission denied » ; `FAKE_SSH_DELAY` retarde la réponse en secondes : clone lent). En `pnpm dev:web`, réglage par l'adresse : `?fake_ssh_mode=`, `?fake_ssh_account=`, `?fake_ssh_serve_root=`, `?fake_ssh_allowed_key=`, `?fake_ssh_delay=`, `?ssh_test_timeout_ms=` (délai du test, 10 s par défaut ; les tests e2e du silence le ramènent à 1 s). Le pont lançant un processus par commande, le clone y écrit sa progression dans `clone.progress` et surveille `clone.cancel` (posé par la commande `cancel_clone`) dans le dossier de données ; l'interface de test relit `get_clone_progress` toutes les 100 ms pour émettre l'événement `clone-progress`. Tests Rust : `test_connection_with` reçoit le faux `ssh`, l'échéance et ses variables.
- Tests et captures : le dossier SSH se règle par `OCTOGIT_SSH_DIR` (voir `.env.example`) ; en `pnpm dev:web`, `?ssh_dir=<chemin>` dans l'adresse. Sans l'un ni l'autre, le pont de test n'écrit jamais dans le vrai `~/.ssh` : il utilise `ssh/` sous le dossier de données (`.dev-data/ssh/`, ignoré par Git). Les chemins sous `/Users/<nom>` s'affichent avec `~` (affichage seulement). Le pont de test garde les passphrases dans un faux trousseau fichier `<dossier de données>.keychain-fake.json` (motif `*.keychain-fake.json` ignoré par Git), qui n'existe que dans le pont : l'application livrée utilise toujours le trousseau macOS.
- **Alt+↑ / Alt+↓** montent ou descendent le profil sélectionné ; l'ordre est mémorisé.
- Échap avec des modifications non enregistrées ouvre « Discard changes to profile … ? » : Save (enregistre puis ferme), Discard (ferme sans enregistrer), Cancel (reste avec les modifications).
- Les profils vivent dans `profiles.json` (`version` 2, champ `profiles` dans l'ordre de la liste, chacun avec ses `rules`) sous `OCTOGIT_DATA_DIR`, écrit atomiquement. Un fichier de version 1 (sans règles) est lu avec des règles vides et passe en version 2 à la prochaine écriture. Octogit ne lit ni n'écrit jamais `~/.gitconfig`.
- **Règles de rattachement** (`Matching rules`, sous le formulaire d'un profil enregistré) : **Path rule** ajoute une règle de chemin (`~/Dev/Pro/**` : `~` est le dossier personnel, `*` une partie de nom, `**` n'importe quelle profondeur ; un chemin sans joker vaut pour le dossier et tout ce qu'il contient) et **Remote owner rule** une règle `github.com/<owner>/*`, lue sur le remote `origin` seulement (URL SSH `git@github.com:owner/repo.git` ou HTTPS `https://github.com/owner/repo.git` ; un autre remote comme `upstream`, ou l'absence d'`origin`, ne correspond pas). Chaque règle montre son type ; le bouton de retrait la supprime. Les règles sont enregistrées par **Save** (qui reste désactivé tant qu'un motif est vide).
- **Rattachement** : à l'ouverture d'un dépôt (au lancement comme par `RepoPicker`), il est rattaché au profil dont une règle correspond, à condition que les règles d'un seul profil correspondent (plusieurs règles du même profil comptent pour une) ; `ProfileBadge`, dans l'en-tête de `History` et sur chaque ligne de Recent, affiche son état. Sans règle correspondante, ou si les règles de plusieurs profils correspondent, le dépôt reste « No profile » : rien n'est rattaché ni écrit, même si son `.git/config` contient déjà `user.name`, `user.email` ou `core.sshCommand`. L'ordre des profils dans `ProfileSettings` ne sert qu'à l'affichage (liste, menu du badge) : le réordonnancer ne change aucun rattachement. Le choix manuel mémorisé reste prioritaire.
- **`ProfileBadge`** : trois états. _Conforme_ : nom et couleur du profil (la même pastille que dans la liste de `ProfileSettings`). _Non conforme_ : « ⚠ Work · identity mismatch », distinct de l'état conforme par le signe et le texte, sans recours à la couleur ; c'est le cas d'une valeur locale qui diffère du profil (voir `IdentityMismatch`), et aussi d'un profil à signature cochée dont la clé publique (`.pub`) manque : rien n'est alors écrit dans le dépôt, sans message. C'est aussi le cas d'un dépôt dont le `.git/config` local contient au moins une des clés `user.name`, `user.email`, `core.sshCommand` sans que les quatre valeurs soient celles du profil, même si la différence est une valeur absente (par exemple `user.email` seul) ; la lecture sans écriture de Recent donne le même état que l'ouverture. Seul un dépôt sans aucune de ces trois clés est conforme avant l'ouverture (elle écrit ses valeurs). _« No profile »_ : aucun profil rattaché (le texte reste « No profile » ; le menu permet d'en choisir un).
- **Menu du badge** (clic sur `ProfileBadge` dans l'en-tête de `History` ; Échap ou un clic ailleurs le ferme) : « Fix repository identity » en tête quand le badge est non conforme (même écriture que dans `WorkingChanges`), puis les profils dans l'ordre de la liste (le profil actif coché), **Edit profiles…** (ouvre `ProfileSettings` sur le profil actif) et **Reset to rules**. Choisir un profil le rattache à la main : le choix est mémorisé, ses valeurs sont écrites dans le `.git/config` local seulement si aucune de `user.name`, `user.email`, `core.sshCommand` n'existe ; sinon `IdentityMismatch` s'affiche (rien d'écrit, rien de complété) si un réglage local diffère ou manque ; il est gardé après relance, même si une règle désigne un autre profil. **Reset to rules** efface le choix manuel et rattache le dépôt par les règles (écriture ou `IdentityMismatch` comme à l'ouverture) ; il est désactivé sans choix manuel.
- **Ce qui est écrit** dans le `.git/config` local du dépôt, par `git config --local`, clé par clé, sans toucher au reste (remotes, branches) : `user.name`, `user.email`, `core.sshCommand` = `ssh -F none -i <clé> -o IdentitiesOnly=yes -o IdentityAgent=none` (seule la clé du profil est présentée ; `-F none` : `~/.ssh/config` n'est pas lu, ses alias d'hôte ne servent donc pas aux dépôts rattachés), et la signature : cochée, `commit.gpgsign=true`, `gpg.format=ssh`, `user.signingkey=<clé publique du profil>` ; décochée, `commit.gpgsign=false` et aucune des deux autres clés. Jamais dans `~/.gitconfig` : toute écriture utilise `--local`. Un `.git/config` déjà conforme n'est pas réécrit (identique octet pour octet). Sans dialogue, ces valeurs ne sont écrites que si aucune de `user.name`, `user.email`, `core.sshCommand` n'existe dans le `.git/config` local. Dès qu'une de ces clés existe et que les quatre valeurs ne sont pas toutes celles du profil (valeur différente, ou valeur absente comme `core.sshCommand` quand seul `user.email` est présent), rien n'est écrit ni complété : `IdentityMismatch` s'affiche (voir ci-dessous). « No profile » n'écrit rien.
- **`.git/config` local différent du profil** (une des quatre valeurs `user.name`, `user.email`, `core.sshCommand`, signature, différente ou absente dès qu'une des trois premières clés existe) : à l'ouverture, au choix d'un profil dans le menu du badge et à « Reset to rules », `IdentityMismatch` (« Local Git config differs from profile Pro ») affiche le chemin du dépôt, l'origine du rattachement (« matched by rule `<motif>` » ou « manual choice »), « Nothing has been written. » et un tableau profil / local des quatre valeurs (lignes `user.email`, `user.name`, `core.sshCommand`, signature) ; chaque écart porte le signe « ≠ » et le texte « differs » (jamais la couleur seule), une valeur absente s'affiche « not set » et, quand elle cause l'écart, porte aussi « ≠ differs ». Tant qu'aucun choix n'est fait, le `.git/config` reste identique octet pour octet. **Overwrite with profile Pro** écrit les valeurs du profil (mêmes clés que ci-dessus, clés ciblées par `git config --local` ; `commit.gpgsign=false` si la signature est décochée, `gpg.format` et `user.signingkey` retirés) et ferme le dialogue. **Import local config into Octogit…** ouvre `ProfileSettings` sur un nouveau profil pré-rempli avec `user.name`, `user.email`, la clé de `-i <clé>` dans `core.sshCommand` et la signature (cochée si `commit.gpgsign=true`) ; le nom reste à saisir et le `.git/config` n'est pas touché tant qu'on n'a pas fait Save ; **Save** crée le profil, rattache le dépôt à lui, écrit alors ses valeurs dans le `.git/config` comme Overwrite (clés ciblées, forme d'Octogit pour `core.sshCommand`) et revient à `History`, conforme. **Cancel** ou Échap ferme le dialogue sans rien écrire (Commit et Push restent bloqués, voir « Commit et Push bloqués » ci-dessous) ; il réapparaît à la prochaine ouverture, y compris pour un dépôt laissé tel quel après Save d'un profil. Sous le tableau, il dit « Until a choice is made, Commit and Push stay blocked. ». Un `core.sshCommand` importé de forme différente (par exemple `ssh -i <clé>`) est donc remis dans la forme d'Octogit au Save : `IdentityMismatch` ne revient pas.
- **Commit et Push bloqués** : un dépôt dont l'identité est non conforme (une valeur locale diffère, ou les valeurs du profil ne peuvent pas être calculées, par exemple signature cochée sans `.pub`) ou « No profile » ne peut ni créer de commit (Commit, Cmd+Entrée, Amend) ni pousser, sans contournement : `PushButton` est désactivé, sans compteur, avec la même raison que Commit écrite à côté (« Identity does not match profile Work. », ou « No profile. » ; Commit dit « No profile »), jamais de « Force push ». Le garde est refait côté Rust au moment de l'action (`ensure_conform`, avant tout `git push`, publication d'une branche « Not published » et Force push compris), sans se fier à l'interface : un refus ne crée aucun commit, ne lance aucun `git push` et ne change pas la branche distante. Aucun réglage ne le désactive. « Fix repository identity » (`WorkingChanges` ou menu du badge), Overwrite, ou le choix d'un profil levent le blocage ; Checkout, Branch, Reset… restent disponibles. Un push lancé depuis le terminal échappe au contrôle d'Octogit.
- **Commits à pousser** : les commits de la branche courante absents de toute branche distante (`refs/remotes/<remote>/*`) du remote cible (celui de la branche suivie, sinon `origin`) sont vérifiés par rapport au profil rattaché, à chaque lecture (commande `get_push_check`, relue à l'ouverture, après fetch, commit, push, pull, au changement de `.git/config` et au retour dans la fenêtre : un commit fait au terminal, même par `git -c user.email=… commit`, est vu au retour). Un commit est **fautif** si son committer (nom ou adresse) diffère du profil, ou si son auteur a l'adresse d'un autre de mes profils ; les adresses se comparent sans égard à la casse. Un auteur qui n'est aucun de mes profils (un collègue) ne rend pas fautif, et les commits déjà présents sur une branche distante (par exemple `origin/develop` fusionnée) ne comptent pas. Un commit dont l'auteur et le committer sont en cause est classé « committer ». Un commit fautif bloque `PushButton` : « Push 2 » désactivé, avec « 1 of 2 commits authored as jag@perso.fr. Profile Work expects jag@work.fr. » (ou « … committed as <nom et adresse>. Profile Work expects <nom et adresse de Work>. », qui prime si les deux cas existent), suivi de la liste des commits à pousser (SHA abrégé, résumé, « ✕ author », « ✕ committer » ou « ✓ »). Dans le graphe, le nœud de chaque commit fautif porte une marque « ✕ » (nom accessible « ✕ author » ou « ✕ committer ») et sa ligne dit le champ en toutes lettres ; les autres n'en ont pas. Le garde est refait côté Rust avant tout `git push` (`ensure_pushable`, après celui de l'identité du dépôt), avec la même raison. Aucune fixture nouvelle : les cas se fabriquent avec `fixtures/push.sh` (scénario `published`) et `git`.
- **Fix commit identity** : dans l'état de `PushButton` bloqué par des commits fautifs (jamais dans celui bloqué par l'identité du dépôt, où « Fix repository identity » reste seul), le bouton principal « Fix commit identity » réécrit en un seul geste chaque commit fautif à pousser, quelle que soit sa position (commande `fix_commit_identity`, crate `git`, fonction `rewrite_identity`). Chaque commit réécrit a Work (le profil rattaché) comme committer, avec la date de la réécriture, et Work comme auteur seulement si son auteur était un autre de mes profils (la date d'auteur d'origine est gardée) ; un collègue (`alice@client.fr`, aucun de mes profils) reste auteur, avec son nom, son adresse et sa date. Les commits réécrits sont signés selon Work (`commit.gpgsign`, `gpg.format`, `user.signingkey` du `.git/config` local ; `~/.gitconfig` n'intervient pas). Messages et contenus sont inchangés ; la topologie est conservée (un merge reste un merge). Un commit à pousser non fautif au-dessus d'un commit réécrit est recréé sur son nouveau parent avec ses auteur, committer, dates, message et contenu d'origine, signé selon Work ; les autres, et tout commit déjà présent sur une branche distante, ne sont jamais réécrits. La réécriture se fait sans checkout (`git commit-tree`, puis une seule mise à jour de la branche courante par `git update-ref` avec sa valeur ancienne attendue) : l'arbre de travail et l'index ne changent pas, et en cas d'échec la branche garde son pointeur. L'ancien pointeur reste dans le reflog (pas de copie de sauvegarde). Ensuite, la liste est relue, plus aucun commit n'est fautif, les marques du graphe disparaissent et « Push n » est actif : un push normal, jamais « Force push ». Le garde d'identité du dépôt est refait côté Rust (non conforme ou « No profile » : refus avec la même raison, rien n'est réécrit). Avec des modifications non commitées (indexées ou non), la réécriture est refusée avec « Commit or stash your changes before fixing commit identity. » affiché dans l'état bloqué, sans rien changer. Si la signature échoue, tout est refusé (« The commits could not be signed. Nothing was changed. ») et la branche reste inchangée. Elle passe par la même garde que le fetch et le push (jamais en même temps qu'un fetch du même dépôt). La correction à la main au terminal n'est plus nécessaire. Aucune fixture nouvelle (cas fabriqués avec `fixtures/push.sh`, scénario `published`, et `git`).
- **Rattachement manuel mémorisé** : le dépôt rattaché par Import est noté dans `repositories.json` (`version` 6, champ `manual_profiles`, clé : chemin du dépôt, valeur : identifiant du profil). Il est prioritaire sur les règles et gardé aux ouvertures suivantes ; si ce profil est supprimé, le dépôt s'affiche « No profile » (il ne retombe pas sur les règles). Un fichier de version 2 à 4 est lu sans rattachement manuel et passe en version 6 à la prochaine écriture. Ce stockage sert aussi au menu du badge (choix d'un profil, « Reset to rules » qui efface l'entrée) et au clone (le profil choisi est mémorisé ici avant l'ouverture).
- **Modifier un profil** : **Save** réécrit, sans autre geste, le `.git/config` local (`user.name`, `user.email`, `core.sshCommand`, signature, clés ciblées par `git config --local`, autres sections intactes) des dépôts récents rattachés à ce profil dont les quatre valeurs sont toutes celles de l'ancienne version. Un dépôt dont un réglage local diffère, ou manque alors qu'une autre des trois clés (`user.name`, `user.email`, `core.sshCommand`) est présente, reste identique octet pour octet ; Save le liste (« 1 repository not updated: local settings changed by hand. », puis le chemin de chacun) et `IdentityMismatch` s'affiche à sa prochaine ouverture. Un dépôt rattaché sans aucune de ces trois clés n'est pas visé : il n'est ni réécrit ni listé, et reçoit le profil à sa prochaine ouverture. Un dépôt dont la réécriture échoue (signature cochée sans clé `.pub`, `git config` en erreur) est listé à part (« 1 repository not updated: writing to .git/config failed. », puis son chemin), sans être compté parmi ceux changés à la main. Un dépôt qui n'est plus sur le disque est ignoré. Changer seulement le nom, la couleur ou les règles ne réécrit rien.
- **Delete profile** : une confirmation (« Delete profile Work? ») liste les dépôts récents rattachés ; Cancel ne change rien. Après confirmation, le profil disparaît de `profiles.json`, aucun `.git/config` n'est touché (ni clé SSH, ni fichier) et ces dépôts s'affichent « No profile ».

## Livraison

Octogit est livré en `.dmg` pour puces Apple, signé ad hoc (sans compte Apple Developer ni notarisation). Pas de mise à jour intégrée : on met à jour en téléchargeant la nouvelle version.

### Construire

```sh
pnpm tauri build
scripts/check-bundle.sh   # monte le .dmg (lecture seule) et vérifie Octogit.app : signature ad hoc, arm64, macOS 13 minimum, icône fournie
```

Le `.dmg` est dans `target/release/bundle/dmg/` (`Octogit_<version>_aarch64.dmg`), l'application dans `target/release/bundle/macos/Octogit.app`.

### Installer

Ouvrir le `.dmg`, glisser `Octogit.app` dans `Applications`.

### Premier lancement (version téléchargée)

macOS bloque une application non notarisée téléchargée. Une seule fois :

- macOS 15 et plus récent (dont macOS 26) : Réglages Système › Confidentialité et sécurité › **Ouvrir quand même** (après une première tentative de lancement). Le clic droit › Ouvrir ne contourne plus Gatekeeper ;
- macOS 13 et 14 seulement : clic droit sur `Octogit.app` › **Ouvrir**, puis confirmer (la voie des Réglages Système marche aussi).

### Publier une release (manuel, sur `jeanalexandre/octogit`)

1. Monter la version dans `package.json`, `src-tauri/tauri.conf.json` et le `Cargo.toml` racine (`[workspace.package]`, dont `src-tauri/Cargo.toml` hérite), puis lancer `pnpm tauri build` et `scripts/check-bundle.sh`.
2. Créer un tag `v<version>` et le pousser sur `jeanalexandre/octogit`.
3. Sur GitHub : Releases › Draft a new release, choisir le tag, rédiger les notes.
4. Attacher `target/release/bundle/dmg/Octogit_<version>_aarch64.dmg`, puis publier.

Aucune automatisation ni CI de release.

## Données

Octogit écrit ses fichiers JSON dans `OCTOGIT_DATA_DIR`. En développement et en test, le défaut est le dossier `.dev-data/` du repo (ignoré par Git) ; jamais `~/Library/Application Support/Octogit/`, réservé à l'application livrée. Les variables `OCTOGIT_DATA_DIR` et `OCTOGIT_PORT` se lisent dans `.env.local` à la racine (non versionné, ignoré par Git ; copier `.env.example`), sans préfixe de commande : `pnpm dev:web` et `pnpm e2e` le chargent par Node (`--env-file-if-exists`). Une variable déjà posée dans le shell l'emporte. Lancer toujours par ces scripts pnpm, jamais `npx playwright` ni `cargo run` en direct (ils ne lisent pas `.env.local`). Sous `pnpm e2e`, le port suit `OCTOGIT_PORT` mais les données de test restent dans un dossier temporaire. Une valeur absolue est préférable pour `OCTOGIT_DATA_DIR`. `OCTOGIT_PORT` n'agit que sur `pnpm dev:web` : `pnpm tauri dev` sert toujours sur le port 1420, donc deux `pnpm tauri dev` en parallèle se bloquent. Voir `.env.example`.

## Organisation du repo

- `crates/git` (`octogit-git`) : lecture des dépôts avec `gix`
- `crates/identity` (`octogit-identity`) : profils d'identité (type `Profile`, ordre) ; clés SSH (module `ssh` : génération, empreinte, `.pub`, par `ssh-keygen`) ; règles de rattachement (module `rules` : Path, Remote owner, un seul profil par dépôt) ; conformité et écriture de l'identité dans le `.git/config` local (module `local`, par `git config --local`)
- `crates/store` (`octogit-store`) : persistance JSON versionnée, écriture atomique
- `crates/platform` (`octogit-platform`) : intégrations propres à macOS
- `src-tauri/` (crate `octogit-app`) : commandes et événements Tauri, sans logique
- `src/lib/screens/`, `src/lib/components/` : écrans et composants Svelte ; `src/lib/styles/tokens.css` : tokens de couleur ; `src/lib/bindings.ts` : généré
- `assets/icons/` : icônes fournies, source de `src-tauri/icons/` (`octogit.icns` copié tel quel en `icon.icns` ; `octogit.ico` n'est pas embarqué, macOS seul). Régénérer les PNG : `pnpm tauri icon assets/icons/octogit-original-1024.png --output <dossier temporaire>`, ne garder que `32x32.png`, `128x128.png`, `128x128@2x.png` et `icon.png` dans `src-tauri/icons/`
- `e2e/` : tests Playwright ; `fixtures/` : scripts qui fabriquent les dépôts d'exemple et le faux `ssh` de test
- `brief.md`, `ux.md`, `stack.md`, `specs/`, `ux/`, `plan.md`, `stories/` : livrables de méthode
